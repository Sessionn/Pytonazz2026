## Problemi ancora aperti, in ordine di priorità

### P1 — Credenziale nella configurazione Git locale

L'URL del remote locale include una credenziale di accesso. Questa può comparire nell'output dei comandi diagnostici. Il valore non è riportato nel documento.

**Proposta:** ruotare la credenziale e usare un credential manager oppure autenticazione SSH, con URL del repository privo di segreti. Questa configurazione locale non è stata modificata durante il rilascio.

### P1 — Identificatori cache rinumerati mentre altre sessioni li usano

In `core/cache_db.py:compact_ids` e nelle API DELETE della dashboard gli ID vengono compattati dopo una cancellazione. Un'altra scheda può avere ancora l'ID precedente, ora assegnato a un brano diverso. La successiva cancellazione potrebbe quindi colpire un'altra riga. È un rischio dedotto dal flusso del codice, non una cancellazione eseguita sui dati reali.

**Proposta:** mantenere chiavi primarie stabili e usare un numero progressivo solo nella presentazione; in alternativa aggiungere una versione del dataset e rifiutare con 409 le modifiche provenienti da una vista obsoleta. La modifica richiede una migrazione coordinata con i test che oggi prevedono la compattazione.

### P1 — Verifica TLS disabilitata per i link brevi SoundCloud

`core/source_resolver/ytdlp.py:_resolve_soundcloud_short_url` usa sia `verify=False` sia un contesto urllib con `CERT_NONE`. Non verifica quindi l'identità del server remoto.

**Proposta:** ripristinare TLS verificato e configurare esplicitamente eventuali CA necessarie. La compatibilità con la rete/proxy della VM va verificata prima del rilascio; il workaround non è stato rimosso alla cieca.

### P2 — Stream SSE e memoria

`core/runtime.py:start_dashboard_thread` configura otto thread Waitress; ogni stream SSE a lunga durata ne occupa uno. Più schede dashboard/console possono esaurire i worker disponibili. Inoltre `core/dj_access.py:subscribe` crea code senza limite: un client lento può accumulare snapshot.

**Proposta:** code limitate all'ultimo snapshot, limite di stream per sessione e carico misurato con più client; in seguito separare gli stream dal server delle API. Non è stato eseguito un test di carico sulla VM.

### P2 — Persistenza JSON e ripristino

Compleanni, welcome e configurazione scrivono direttamente sui file. In particolare lo store compleanni registra un errore di scrittura senza propagarlo, quindi un comando può confermare una modifica non salvata. Il ripristino backup scrive prima di validare tutto il contenuto; il limite di 10 MB controlla l'archivio compresso, non la somma dei file decompressi.

**Proposta:** file temporaneo e sostituzione atomica, errori restituiti ai comandi, validazione completa prima del restore e limite cumulativo dei byte decompressi. Valutare SQLite anche per le configurazioni con accessi concorrenti.

### P2 — Compleanni a mezzanotte e liste lunghe

Il ciclo invia gli auguri soltanto nel minuto 00:00: un riavvio o una temporanea indisponibilità in quel momento fa saltare gli auguri. La lista usa `date.today()` mentre il ciclo usa Europe/Rome. Si conserva inoltre un solo ID messaggio: le pagine successive non sono gestite dal refresh, e una lista inviata altrove può non essere ritrovata nel canale configurato. I blocchi sono paginati per numero di date, non per lunghezza dei contenuti Discord.

**Proposta:** registro persistente degli invii giornalieri con recupero dopo il riavvio, timezone unica, memorizzazione di canale e di tutti gli ID delle pagine, suddivisione in base ai limiti effettivi degli embed.

### P2 — Riproducibilità del deploy e documentazione

L'avvio aggiorna yt-dlp automaticamente con pip; molte dipendenze hanno solo una versione minima. Un riavvio può quindi cambiare il software installato. La guida VM descrive ancora `main-2` e screen, mentre la verifica SSH ha trovato `link-up` e tmux. Il venv Windows locale punta a un interprete Python 3.10 non più disponibile.

**Proposta:** file di dipendenze bloccate e aggiornamenti verificati separatamente; guida VM allineata allo stato reale; ricreazione del venv locale. La presenza della sessione tmux da sola non dimostra la salute del bot: servono log, connessione Discord e risposta HTTP.

### P2 — Protezioni web da completare

Non c'è un token CSRF dedicato per tutte le operazioni con sessione; la protezione corrente dipende anche da cookie SameSite e comportamento del browser. Il rate limit del login è in memoria, senza pulizia globale delle vecchie chiavi. L'autenticazione degli stream è valutata all'apertura: rivedere anche revoca/scadenza delle sessioni durante stream lunghi.

**Proposta:** CSRF uniforme, scadenze e pulizia del registro dei tentativi, verifica periodica delle autorizzazioni degli stream. Non è stato svolto un penetration test.

### P3 — Manutenibilità e performance

- Resolver oltre 2.000 righe, cache quasi 1.900, cog musica e moderazione oltre 1.000: separare orchestrazione, policy e accesso ai dati.
- CSS della console contiene varie successive riscritture degli stessi selettori; il tema condiviso risolve i conflitti visibili, ma un consolidamento completo ridurrebbe il debito tecnico.
- Le API degli elenchi non espongono una paginazione uniforme e alcune viste filtrano in memoria nel browser: prevedere paginazione server quando cresce l'archivio.
- Alcuni commenti del resolver hanno caratteri corrotti; ripulire la codifica in un cambiamento dedicato.
